System Design Document (SDD): ZAPRICA
(Enterprise AI OSINT Platform)
1. System Overview
ZAPRICA is an enterprise-grade, autonomous AI Open-Source Intelligence (OSINT) platform. It replaces manual API-based intelligence gathering with an autonomous agentic workflow. The system provisions AI agents capable of reasoning, planning, and executing authorized cybersecurity tasks through sandboxed web browsers and shell environments.
2. High-Level Architecture
The system follows a decoupled, asynchronous microservices architecture to ensure the long-running nature of OSINT investigations does not block system resources.
The architecture is divided into four primary layers:
Presentation Layer: React/Next.js dashboard rendering a live node-link graph.
API Gateway & Auth Layer: FastAPI handling user authentication, RBAC, and case management.
Orchestration Layer: Temporal.io server managing stateful LangGraph workflows.
Execution Layer (Isolated Workers): Dedicated worker nodes for Browser tasks, Shell tasks, and API calls.
3. Core Component Design
3.1 The Execution Orchestrator
OSINT investigations often encounter rate limits or require deep recursion, meaning processes can run for hours.
Technology: LangGraph + Temporal.io1.
Design: LangGraph acts as the state machine defining the autonomous loop (Plan -> Execute -> Extract -> Graph). Temporal.io orchestrates these graphs as durable executions, ensuring that if a worker crashes or a network times out, the exact state of the investigation is preserved and resumed automatically3.
3.2 Browser Agent Worker
To extract intelligence from dynamic, JavaScript-heavy sites that lack public APIs, ZAPRICA utilizes a headless browser agent.
Technology: Playwright and the browser-use Python library4.
Design: Instead of overwhelming the LLM's context window with raw HTML DOMs, the worker utilizes an Accessibility Tree extraction strategy. The page is parsed into a simplified tree of interactive elements, assigning unique IDs that the LLM references to execute spatial commands (e.g., click(element_12))7.
Human-in-the-Loop (HITL): If the worker encounters a strict CAPTCHA, it suspends the Temporal workflow and alerts the dashboard for human intervention, resuming automatically once solved6.
3.3 Shell Agent Sandbox
Cybersecurity analysts require command-line utilities (e.g., whois, nmap).
Technology: Docker, Linux seccomp.
Design: The LLM never accesses the host shell. Every shell tool request spins up an ephemeral, single-use Docker container9. The container enforces a read-only filesystem and a strict seccomp profile that drops dangerous system calls, limiting execution strictly to a whitelist of authorized binaries10.
3.4 Tool Registry (Plugin System)
ZAPRICA integrates diverse OSINT tools uniformly without hardcoding them into the main agent loop.
Technology: Model Context Protocol (MCP)11.
Design: The system acts as an MCP Server exposing tools via JSON-RPC 2.0 messages13. The agent discovers tools using tools/list and executes them via tools/call14. This standardized schema validation prevents malformed arguments from reaching the execution layer.
4. Database & Knowledge Graph Design
A unified database architecture reduces latency and deployment complexity compared to maintaining separate relational and graph clusters.
Technology: PostgreSQL + Apache AGE extension17.
Design: Apache AGE provides openCypher graph querying capabilities directly within PostgreSQL19. Standard SQL handles tenant isolation and case management, while AGE manages recursive entity mapping.
4.1 Schema Overview
Users/Tenants (SQL): users, organizations, cases, audit_logs.
Graph Nodes (AGE): Person, Organization, Domain, IP, Email, File_Hash.
Graph Edges (AGE): resolves_to, associated_with, mentions.
Evidence Model (SQL): Every edge mapped in the graph points to a relational row storing the source URL, an ISO 8601 timestamp, a SHA-256 cryptographic hash of the raw evidence, and an S3 bucket URI containing the raw screenshot or log output.
5. Security Architecture (Threat Mitigation)
Because the agent interacts with untrusted external web data, mitigating Prompt Injection is the highest security priority. ZAPRICA addresses the OWASP Top 10 for LLM Applications (2025/2026)20.
5.1 Dual LLM (DualView) Pattern (Mitigates OWASP LLM01)
To prevent Indirect Prompt Injection (IPI), where a malicious web page instructs the agent to execute unauthorized commands22, ZAPRICA enforces strict Information Flow Control (IFC)24.
Privileged Planner LLM: Responsible for logic and tool execution. It is strictly quarantined from reading raw web data.
Quarantined Extractor LLM: Reads the raw, potentially malicious web pages. It has zero tool-calling privileges and is constrained strictly to structured JSON output25.
Result: Malicious instructions on a target website are processed as inert text by the Extractor, preventing the Planner from being hijacked.
5.2 Excessive Agency Mitigation (Mitigates OWASP LLM06)
Mitigated by strictly defining execution scopes in the MCP Tool Registry and validating all JSON-RPC arguments against regex allowlists prior to Docker execution28.
6. Privacy & Compliance Controls
Note: Subject to legal counsel review.
Data Protection: Designed to comply with the Indian Digital Personal Data Protection (DPDP) Act, 2023, specifically leveraging Section 3(c)(ii) regarding personal data made voluntarily publicly available29.
Auditability: Immutable logging of all agent actions, ensuring analysts can prove intelligence was gathered from lawful, public sources.
Data Minimization: Automated TTL (Time-To-Live) purging of investigation data once a case is closed.
7. Basic Data Flow (Investigation Loop)
Seed Input: User initiates a case with a seed (e.g., Domain: example.com).
Discovery: The Privileged Planner queries the MCP Registry (tools/list) and selects a relevant tool (tools/call).
Execution: The Temporal orchestrator routes the request to the appropriate isolated worker (Browser or Shell).
Extraction: The worker fetches the raw data and passes it to the Quarantined Extractor LLM.
Sanitization: The Extractor returns a sanitized JSON array of identified entities.
Resolution: The backend normalizes the entities, hashes them, and checks PostgreSQL/AGE for duplicates.
Graphing: New nodes and edges are inserted; evidence is hashed and backed up to S3.
Re-Evaluation: The Planner evaluates the new nodes and decides if further pivoting is required.
